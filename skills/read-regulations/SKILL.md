# Read Regulations — the Regulation Firewall

## Dispatch the named agent — the contract lives in its body

This skill is a **thin main-session pointer**. The firewall *contract* — the boundary, the gate-defined read loop, the citation-fidelity gates, the render-cleanup gate, the cache protocol, and the `<thalura-digest version="1">` envelope mandate — is the fixed system prompt of the named agent **`agents/read-regulations.md`**. It is **not** restated here and is **not** relayed in the dispatch prompt.

**When a firewall read is needed, the main session dispatches the named agent: `subagent_type: "thalura:read-regulations"`** (the Agent-tool dispatch handle). This is a hard mandate, not a suggestion: do **not** hand-write a `general-purpose` firewall prompt that restates the boundary or the read loop — the contract is single-sourced in the named agent's body, and dispatching it by name is how that single source takes effect. **Fan out — dispatch one named `thalura:read-regulations` reader per document in the dispatched set, all in ONE tool batch; each reader receives exactly one document with its `Read scope`, its matching page-map sidecar slice, and the regulatory-hierarchy context; each reader's dispatch prompt begins with exactly one `document_id:` line — the registry id of its single document** (the same four read inputs as before — now sliced per document, never the whole plural set to one reader). **Beside that line, each dispatch declares its scope: one `section_anchor:` line per section of that document's `Read scope`, each on its own line, carrying that section's heading verbatim as the page-map spells it — never a shortened, re-cased or paraphrased form — and none at all when the `Read scope` is `full`** (enumerating a whole document's headings only trips the same arity rule a multi-section declaration trips, and costs tokens to reach the same outcome). The dispatched set is the registry-resolved INCLUDE set minus every document whose needed sections are already covered by a version-stamp-valid cache entry. Concurrency is gate-defined (dispatch the batch; nothing caps the number of readers — escalate to sequential waves only on an observed queue/reject/fail-to-start; every dispatched document returns a verified digest — none silently dropped). Each reader returns **only its own document's digest**; nothing else crosses back.

**A remembered digest can be re-read, once, when it does not answer the question.** A dispatch is normally turned back before any reader starts whenever the sections it needs are already remembered — that is the fast path and it is normally correct. It is not always: the remembered passage may cover a different section than the question needs, or the right section without the lines that would settle it. A dispatch prompt may therefore carry **one further line-anchored key besides `document_id:`** — a whole line reading exactly `cache: force-reread` — which makes the read ignore what is remembered for those sections and open the pages again, replacing the remembered passage with what it finds. **What it replaces is the section it reads.** Where the remembered digest covered the right section thinly, the re-read overwrites that entry and the repair holds; where it covered a *different* section than the question needed, the re-read rebuilds the requested section and leaves that other entry untouched — so there the key is a per-dispatch bypass, attached again on each dispatch about that section, not a one-off fix. It is **exceptional and deliberate**: attach it only after reading a returned digest and judging it insufficient, only to a regulation dispatch, and only once per question — a re-read that still does not answer it means the document does not say so.

**The dispatched documents are named to the teacher before the batch goes out.** In `conversation_language` and by their teacher-recognizable names, the main session says which documents it is about to read — an announcement, not a request: nothing waits on an answer and the batch dispatches immediately. The naming is what keeps a read traceable while it is happening; the core skill owns its wording and the per-document progress entries that accompany it.

**Graceful-degradation backstop.** If the named dispatch does not resolve, the dispatch falls back to `general-purpose`. On that fallback path a host-executed `PreToolUse`-on-`Agent` hook injects the envelope mandate into the dispatched prompt, so the `<thalura-digest version="1">` envelope emission stays in force regardless. A missed named dispatch is therefore **no worse than the prior behaviour** — the digest still comes back enveloped (host-hook persistence applies on the CLI runtime; the in-runtime persist path that also covers the isolated-VM runtime requires the named firewall agent).

## The cache round-trip — looked up before dispatch, persisted by the agent

The session digest cache lets downstream tasks reuse a digest without re-running the heavy read. The round-trip is **split across the boundary**, and the two halves are not symmetric:

**The lookup happens *before* dispatch — it is a structural gate on the dispatch path, not a step anyone performs by hand.** A firewall dispatch whose section is already covered by a fresh cache entry (every bundled-PDF hash and page-map version still current) is **turned back before the reader starts**, and the remembered digest is handed to the main session there and then. A remembered section therefore spawns **no reader at all** and costs no read — it is not a cheaper read, it is *no* read. Nothing in this file, and nothing in the main session, can skip or forget that lookup: it is not remembered prose along a path, it is enforced on the dispatch path itself. This paragraph documents the behaviour; it does not implement it.

**The persistence happens *after* the read, and the agent runs it itself, through its shell** — a `put` against the shipped helper `${CLAUDE_PLUGIN_ROOT}/scripts/cache.py`, keyed off the section identity it resolves. This is what makes persistence work in **both** runtimes: a host-executed cache hook does not fire reliably in the Cowork host/VM split, so the agent persists on its own initiative. (Host cache hooks remain in place as a fail-open backup for the CLI runtime, where they do fire; `cache.py put` is idempotent, so a double-write is safe.)

The cache is **internal-only**: never a deliverable, never shown to the teacher, never previewed. The cache schema, keying, freshness gate, and the full persistence contract live in the named agent's body and `${CLAUDE_PLUGIN_ROOT}/references/schemas/digest-cache.md`; they are not restated here.
