# Thalura Plugin — Versioning & Update Flow

> Version numbering, changelog format, and the release process are defined in the root `VERSIONING.md` (the canonical source). This document covers only how the plugin **detects and applies** an update at runtime.

---

## Version Tracking

### Source of Truth

| File | Contains | Updated by |
|---|---|---|
| `.claude-plugin/plugin.json` | Current plugin version | Plugin author (on release) |
| `<WORKSPACE_ROOT>/data/version.json` | Last-seen plugin version in this project | Core skill Step 1 (after update flow) |

### `<WORKSPACE_ROOT>/data/version.json` Schema

```json
{
  "plugin_version": "1.0.0",
  "updated_at": "2026-03-23T10:00:00Z"
}
```

Created during `/thalura:setup`. Updated by Step 1 after processing a version mismatch.

---

## Update Detection

### Local Version Mismatch (Core Skill Step 1)

At the start of every Thalura session, the core skill compares:
- `plugin.json` → `version` (current plugin version)
- `<WORKSPACE_ROOT>/data/version.json` → `plugin_version` (last-seen version)

If they differ, the plugin was updated since the last command. The update flow runs.

---

## Update Flow

When a version mismatch is detected in Step 1:

1. **Read changelog:** Extract entries from `CHANGELOG.md` between the old and new versions.
2. **Copy new config defaults:** For each file in `config-defaults/`, if no corresponding file exists in `<WORKSPACE_ROOT>/data/config/`, copy it. Existing files are never overwritten.
3. **Update version file:** Write `<WORKSPACE_ROOT>/data/version.json` with the new version and current timestamp.
4. **Notify teacher:** Display changelog summary in `conversation_language`.
5. **Proceed** with the originally requested command.

> **Steps 2 (copy) and 3 (stamp) run on _any_ version difference, independent of changelog content.** Only step 1 (the changelog extract, feeding the step-4 notification) depends on the changelog. An empty changelog range — as between two `-dev.N` builds, which carry only `## [Unreleased]` and no `## [X.Y.Z]` headings — MUST still copy the config defaults and stamp `version.json`. A changelog with no entries in the range is never a reason to skip the copy or the stamp.

> **Deterministic path.** The compare→copy→stamp is performed deterministically by `scripts/version-migrate.sh` at core startup Step 0d, right after the workspace root is bound. The prose in this section (and Step 1) is the **retained backstop** — the model-side confirmation and hook-absent floor — not the only path. Re-running the migration is a strict no-op once the versions match.

### Protected Files (NEVER Touched)

These files are owned by the teacher or generated by commands. The update flow never reads, modifies, or overwrites them:

- `<WORKSPACE_ROOT>/data/profiles/teacher-profile.json`
- `<WORKSPACE_ROOT>/data/profiles/school-config.json`
- `<WORKSPACE_ROOT>/data/profiles/teacher-preferences.json`
- `<WORKSPACE_ROOT>/data/profiles/teacher-observations.json`
- `<WORKSPACE_ROOT>/data/config/naming-conventions.json` (and any future teacher-override config)
- `<WORKSPACE_ROOT>/data/school-years/` (all class definitions, school year plans)
- `<WORKSPACE_ROOT>/data/regulations/sic/` (school-internal curriculum files)
- `<WORKSPACE_ROOT>/data/library/` (library entries and materials)
- `<WORKSPACE_ROOT>/data/exam-formats/` (user-defined exam formats)
- All generated `.docx` output files

### Auto-Updated

- `<WORKSPACE_ROOT>/data/version.json` — updated to new version
- New config defaults — only if the file does not yet exist in `<WORKSPACE_ROOT>/data/config/`
- `<WORKSPACE_ROOT>/data/README.md` — seeded only if the file does not yet exist; never overwritten — by setup, the update cue, or the scaffold-completion routine

## Changelog

The changelog lives at `CHANGELOG.md` and follows the [Keep a Changelog](https://keepachangelog.com/) format. Each version entry is delimited by `## [X.Y.Z]` headings, enabling Claude to extract entries between any two versions **for the notification summary only**. This delimiting drives the changelog summary the teacher sees — it does **not** gate the config-default copy or the `version.json` stamp. Between two `-dev.N` builds there are no `## [X.Y.Z]` headings (only `## [Unreleased]`), so that range is legitimately empty; the copy and stamp still run on the version difference regardless.

The changelog is critical for regulation update traceability — new A-Hefte (Schwerpunktthemen) and updated curriculum standards (Bildungspläne) are documented here.
